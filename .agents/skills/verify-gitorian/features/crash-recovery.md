# Crash recovery

Use `pnpm build`, then `pnpm test:e2e crash-recovery startup-recovery settings-refresh`. The shared fixture owns disposable profiles, native process cleanup, screenshots, traces and source identity. No personal journal or provider credentials are used.

## User entry points

- After an unexpected exit, open the app: automatic acquisition, provider maintenance and updates remain paused while cached work and writing stay available. A normal Arc toast offers only Copy diagnostic report. The existing refresh control becomes Resume automatic refresh, which explicitly restores admission before refreshing. Reading state, copying or dismissing the toast never resumes work; closing without resuming preserves the paused disposition next launch.
- Copy diagnostic report from that toast or inside Technical details on the startup failure surface. Require native clipboard confirmation, failure/retry feedback and privacy-safe content. Startup recovery keeps Retry as its sole top-level action and has no Save control. Settings has no Diagnostics section. The independent Windows dialog retains native Copy/Save using the same report representation; raw technical error text has no separate share path.
- A storage stall changes the existing refresh control to Reopen journal. It must reopen through the diagnostic action without clearing quarantine or dispatching an ordinary refresh.
- On Windows, an independent native dialog offers Wait, Copy diagnostic report, Save report and Restart in recovery during sustained main/renderer/storage failure and after unexpected desktop exit. The test automates only native dialog responses. Watchdog liveness, process creation, report transport and native clipboard stay real.
- Restart in recovery warns about unsaved changes, attempts the current writing checkpoint/cooperative quit, then verifies/terminates only the owned Windows process tree when necessary. The replacement must regain the original profile lease, stay in recovery and retain acknowledged writing plus any durable renderer recovery copy.

## Owning scenarios

`tests/e2e/crash-recovery.spec.ts` owns contextual report copy, native clipboard failure/retry, 320px toast action geometry, keyboard refresh resumption, independent controls while the main event loop is blocked, and product restart/persistence. Its native helper fixture uses a bounded forty-second loop solely for guaranteed cleanup. The restart scenario explicitly prepares a trace and declares the expected process termination; ordinary journeys still require zero exit. The replacement fixture records its own persisted state and exits cleanly before profile removal.

`tests/e2e/startup-recovery.spec.ts` owns failure/retry, keyboard/focus and safe diagnostic sharing only after expanding Technical details for Hub/workspace. `tests/e2e/settings-refresh.spec.ts` confirms the absent Settings support section. `tests/activity-refresh.test.ts` owns the UI's late-stall/native-reopen admission decision. `tests/e2e/draft-recovery.spec.ts` retains the existing recovery-copy/conflict interaction. `tests/recovery-termination.test.ts` owns actual Windows process identity, descendant cleanup and watchdog-branch survival. `tests/incident-reports.test.ts` owns report projection/caps/retention and unresolved recovery disposition. Existing acquisition/history, records, ApplicationWork and database-worker scenarios own their module contracts; storage timeout must not silently reopen or replay.

Require passed run records, preserved commands/source patches/screenshots/traces, and removed owned profiles. Live recovery is Windows-specific until Linux/macOS native lifetime and packaging journeys have been verified. Native memory dumps and automatic hang profiling are deliberately not collected by this update.
